# Node Agent

沙箱在设计上就是临时的：当沙箱被删除时，它输出到 stdout 和 stderr 的一切都会随之消失。**Node Agent** 是一个可选的 DaemonSet，用于解决这个问题——每个 Linux 节点上一个采集器，监视该节点上的每个沙箱 Pod，并将其输出发送到持久化存储，让记录比产生它们的沙箱活得更久。采集完全发生在节点侧，对工作负载不可见。

## 能力一览

| 能力 | 你能得到什么 |
|---|---|
| 日志采集 | 节点上每个沙箱 Pod 的 stdout/stderr（池化的预热 Pod 被排除——它们不是分配实例） |
| 系统调用观测 | 一个可选的内核级数据源，通过内嵌的 eBPF 程序记录沙箱发起的每次系统调用 |
| 持久化目标 | 阿里云 OSS 或持久化的本地文件——每个 Agent 一个目标；另有一个尽力而为的 stdout 模式用于调试 |
| 投递 | 至少一次、可从崩溃恢复，并为每个流提供显式的完整性标记 |
| 组织方式 | 记录按 集群 / 命名空间 / 沙箱 / Pod 组织，便于下游消费 |
| 安全性 | 以背压代替静默丢弃；拒绝不安全的 bucket 配置 |
| 可观测性 | 存活与就绪分离；指标不含敏感标签 |

## 采集如何工作

Agent 是一条流水线：**source** 产生记录，有界的按沙箱队列承载它们，一个 **sink** 将其写出。三个设计选择塑造了整个系统：

- **Source 与 sink 是编译期注册表，不是插件。** 一次构建内嵌它支持的 source；配置在它们之间选择，遇到未知名称时 Agent 进入未就绪状态，而不是启动一条残缺的流水线。运行时不加载任何代码。
- **队列有界，丢弃策略显式。** 默认的 `block` 策略在 sink 变慢时对 source 施加背压——采集变慢，但不丢失任何东西。备选的 `drop` 策略对内存的限制更严格，并把它丢弃的所有内容计入该流的完整性标记。全局内存预算、按沙箱的队列预算，以及可选的按沙箱限速，防止单个嘈杂的沙箱拖垮节点。
- **失败即关闭，绝不崩溃循环。** 无效配置、损坏或不匹配的恢复状态、或不可用的目标，会让进程保持存活但未就绪，并报告一个命名的原因。它绝不会静默重置并重新采集，也绝不会把进度推进到一个未经验证的目的地。

Pod 的选择基于身份，而不是标签猜测：一个 Pod 只有在携带沙箱身份（沙箱 ID 标签、沙箱容器、其重启次数）且**不是**从池中分配（打了池标签的 Pod 是预热容量，不是沙箱）时才会被采集。

## Source

**`container-logs`**（默认）跟踪节点上沙箱 Pod 的 kubelet 日志文件，并将每个容器流转换为 `container-log` 记录输出。一条由低频协调支撑的 inotify 热路径跟随日志轮转、压缩和文件复用；不完整的 CRI 行会在投递前重新拼接。日志文件通过指纹识别，因此被回收或替换的文件会成为被计入的缺口，而不是被静默拼接的数据。只有当 Pod 已终止且读取持续停留在文件末尾后，流才被终结。

**`syscalls`** 在内核层面记录沙箱的真实行为：一个内嵌的 eBPF 程序挂载到每个沙箱 Pod 的 cgroup 上，为每次系统调用产生一条记录——系统调用编号、宿主机 PID/TID、命令名、时间戳——以 `syscall` 记录输出。内核环形缓冲区溢出、Agent 重启间隔和延迟挂载都会按流跟踪并反映在标记中；容器重启会在排空屏障之后重新绑定跟踪器，因此事件不会跨代错归属。该 source 仅支持 Linux（内核 5.11+、cgroup v2），并需要 BPF 和 PERFMON 能力。

每个 source 拥有自己的记录类型和存储格式；二者都接入同一套标记与恢复机制。

## 记录落在哪里

每个流都会成为一个对象族，布局与现实中的集群结构一致。每种记录类型有自己的对象族（`container-log`、`syscall`），各自拥有独立的编码和标记集合：

```text
<cluster>/<namespace>/<sandbox_id>/<pod_uid>/
  sandbox.log
  sandbox.<generation>.log
  sandbox.finalized.<revision>.json
```

非日志记录类型按同样的规则隔离在单独的 `<cluster>/_streams/<kind>/…` 树中。

`finalized` 标记是一个流的收尾声明——一份累积的、不可变的快照，列出每个已关闭对象及其大小和校验和，供消费者验证。它回答的是事故发生后唯一重要的问题：**这些日志可信吗？**

| 标记状态 | 含义 |
|---|---|
| `complete` | 没有主动丢弃，也没有已知缺口。至少一次投递仍可能包含重复。 |
| `complete-with-drops` | 至少有一条记录被主动丢弃，且受影响的区间已被计入。 |
| `incomplete` | 至少有一个已知区间无法读取，或其覆盖范围无法被证明。 |

这种诚实是刻意的。如果 Agent 在某个流仍然打开时重启，恢复的数据仍会被投递——但下一个标记会是 `incomplete`，因为没有任何东西能证明一次短暂的轮转没有在中断期间消失。消费者得到的是真相，而不是乐观。

## 投递保证

- **至少一次，绝无静默丢失**：一条记录的游标只有在 sink 已持久接受且 source 已确认之后才会前进；终结本身是一个两阶段、可崩溃恢复的事务。重复是可能的；未被计入的丢失则不可能。任何可疑之处都会体现在标记中。
- **严格的按流有序**：一个流同一时刻至多有一个在途批次和一个正在终结的 revision——下一个 revision 只有在前一个标记持久化之后才开始。
- **状态与目的地绑定**：本地恢复状态以所配置目标的摘要为键。损坏或不匹配的状态会让 Agent 进入未就绪——它绝不会静默重置并从头重新采集。
- **有界的资源占用**：本地文件在大小、数量和总容量上限下轮转；基于保留策略的清理是可从崩溃中恢复的——它先把已完成的对象族移入暂存区，只有在移动持久化之后才删除，并且绝不会为了腾出空间而删除另一个 generation。
- **保留策略是运维者的职责**：Agent 负责采集；不制定保留策略。OSS 删除始终通过一个需要显式删除凭据的独立离线清理工具完成——采集凭据永远不拥有删除权限。stdout 调试模式是尽力而为的：它不发布标记，也不做任何持久性声明。

## 安全模型

- **最小特权凭据**：OSS 采集凭据需要追加、读取和写入权限——绝不需要删除权限。
- **拒绝不安全的目标**：开启 bucket 版本控制或 WORM，或者存在重叠的生命周期规则，都会成为永久性的启动错误——会破坏 Agent 完整性假设的配置会被拒绝，而不是绕过。
- **启动时校验宿主机预留**：文件描述符和 inotify 上限、状态与输出的磁盘余量，以及队列预算相对 cgroup 内存限制的配比，都在采集开始之前检查——Helm 资源模式无法表达的问题会让启动失败，而不是日后采集失败。
- **就绪即可信**：`/readyz` 聚合一组命名的、低基数的理由（配置无效、目标不可达、重试循环激活……），只有当全部不适用时才通过。未就绪的 Agent 是可见、可诊断的，而不是在静默丢弃数据。

## 可观测性

存活（`/healthz`）与就绪（`/readyz`）被有意分开：进程可以活着但采集被阻塞，就绪端点会以低基数的原因码说明原因——绝不包含凭据、路径或 bucket 名称。当配置了 OTLP 端点时，Agent 会报告记录数和字节数、主动丢弃、重试和队列深度，并且不使用任何沙箱或 Pod 标识作为标签。

## 启用方式

Node Agent 随 `node-agent` Helm chart 发布，在 umbrella chart 中默认禁用。取值说明——目标类型、OSS 凭据、保留策略和集群 ID——参见 [node-agent chart](https://github.com/opensandbox-group/OpenSandbox/tree/main/manifests/charts/node-agent)；实现细节参见[组件源码](https://github.com/opensandbox-group/OpenSandbox/tree/main/components/nodeagent)。
