# 高可用

Fast Sandbox 的可用性故事源于一个决定：**每个沙箱的意图、放置、策略绑定和观察结果都存放在 Kubernetes CRD 中**，而不是任何组件的内存里。组件之所以可重启，是因为持久状态不属于它们。

## 控制平面刻意保持单一

fast-sandbox 控制器（reconciler + FastPath）以单副本运行，不使用 leader 选举。这是一个设计立场，而非疏漏：

- 变更之所以快，正是因为 FastPath 可以将放置和候选状态保存在内存中；一个多副本控制平面恰恰需要围绕这些状态达成共识。
- 没有任何持久化的东西依赖那块内存。崩溃的控制平面只会丢失进行中的协调工作，而 CR 驱动的协调会重放它们：沙箱、池、模板和快照都会从各自的 CR 重新收敛。

因此，*沙箱*的可用性独立于*控制平面*的可用性：控制平面重启期间，运行中的沙箱继续运行，流量继续流动。

## 通过观察收敛

各处的恢复都采用同一模式 — **提交意图，通过观察持久记录来收敛** — 而不是租约或 leader 选举：

- **快照**：创建快照会提交意图并立即返回；终态从 SandboxSnapshot CR 中观察得到。两台服务器协调快照时会在确定性 CR 上收敛：一方在创建前观察，创建竞争被吸收为 `409`，终态数据库写入以预期的先前状态为条件。
- **出口**：重启时出口进程会清空自身规则并发布一个新的化身 ID；Fastlet 会重放每一个活跃绑定和已到达的钩子，因此主体重新进入默认拒绝状态，只有在数据平面确认就绪后才重新开放。
- **节点**：运行时代理向平台上报 Fastlet 健康状态；丢失的 Fastlet 在 `recoveryTimeoutSeconds` 之后按照沙箱的 `failurePolicy` 处理 — 默认为手动恢复。

## 清理

janitor 按扫描间隔运行，在孤立超时之后移除失败操作产生的孤立制品（过期的 pod、遗留资源）— 它是收敛的补充：协调会完成被中断的工作，janitor 清扫不应再存在的东西。

## 故障是什么样子

| 故障 | 影响 | 恢复 |
|---|---|---|
| 控制平面重启 | 短暂失去变更能力；运行中的沙箱不受影响 | CR 驱动的协调重放意图 |
| Fastlet pod 丢失 | 该 Fastlet 上的沙箱宕机 | `recoveryTimeoutSeconds` 之后按每沙箱 `failurePolicy` 处理；checkpoint（如有）在另一个 Fastlet 上恢复 |
| 服务器重启 | 对沙箱无影响；打开的操作从持久记录恢复 | 相同的观察并收敛模式 |
| 制品存储中断 | 新启动降级为直接拉取；运行中的沙箱不受影响 | 存储恢复后 DART 恢复对等/源站服务 |

暂停/恢复值得一提：暂停会对运行时做 checkpoint 并**释放** Fastlet，因此暂停的沙箱完全不占用计算资源 — 而恢复会落在准入选择的任意 Fastlet 上，不一定是原来的那个。
