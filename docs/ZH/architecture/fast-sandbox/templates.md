# 模板

模板是 Fast Sandbox 在任何请求存在之前就固定工作负载的方式：运行时、镜像、entrypoint 和资源在构建时决定，因此创建 API 只需表达意图 — 哪个模板、谁的沙箱、用多久。`templateId` 与 `image`/`snapshotId` 互斥，按请求指定的工作负载字段（entrypoint、env、resources、volumes）会被拒绝。

## 两层，一个模板

一个模板有意存在于两个地方：

- **服务器持久化的元数据**（SQLite/PostgreSQL）是模板定义和租户所有权的事实来源。模板是租户私有的；目录通过与沙箱相同的服务器提供服务，因此 SDK 以与其他一切相同的认证和租户机制管理模板。
- **`SandboxTemplate` CR** 在 fast-sandbox 一侧驱动实际构建。服务器持久化定义并创建 CR；平台的构建器将其异步转换为黄金镜像制品。模板状态从 CR 观察中收敛 — 与沙箱状态相同的模式。

构建在设计上是异步的：API 立即返回已接受状态，模板在构建报告就绪后变为可用。

## 构建产出什么

`SandboxTemplate` 描述的是一次转换，而不只是复制：一个普通 OCI 镜像加上 OpenSandbox 的 guest 接线，编译成一个不可变的黄金镜像。

- **Guest 接线被注入**：init 路径（PID 1，携带就绪标记和心跳）和 execd 运行时文件始终来自模板 — 由此构建的每个沙箱在构造上就是 execd 就绪的。
- **业务 entrypoint 和环境变量被烘焙进去**：空的 entrypoint 默认为一个保活进程；env 以字面值注入 guest（没有运行时间接层）。
- **运行时形态被声明**：模板指明 Firecracker guest 内核和参考机型；就绪定义了 guest 何时算作已启动。
- **输出按内容寻址**：构建将制品发布到存储，并在 CR 状态中记录清单引用和制品摘要 — 构建是不可变且可验证的，从不在原地变异。

## 使用模板

携带 `templateId` 的沙箱创建会解析到已记录的制品；容量来自被引用的池，而不是模板。因为模板固定了工作负载，每沙箱的行为仅限于意图：身份、TTL、元数据、网络策略和可选的池引用（参见[调度](/architecture/fast-sandbox/scheduling)）。更新模板会重建制品并产生新的摘要 — 既有沙箱继续运行它们被接纳时的修订版本；新创建的沙箱采用新构建。
